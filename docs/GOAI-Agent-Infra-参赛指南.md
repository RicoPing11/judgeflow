## 01 赛道概览

### 1.1 赛道基本信息（PDF 第 1 页）

| 项目 | 内容 |
|---|---|
| 赛道名称 | 赛道一：新智基座｜Agent Infra |
| 赛题名称 | 复杂任务多 Agent 自主协同 |
| 一句话介绍 | 聚焦复杂任务多 Agent 基础设施与协同系统，推动企业级 Agent 从 Demo 走向 Production |
| 关键词 | 多 Agent 协同、AgentTeams、Skill、MCP、RAG、可观测、零人工运维、Agent Infra |

### 1.2 赛道介绍（PDF 第 1 页）

赛道聚焦企业级复杂任务下的多 Agent 基础设施与协同系统。参赛者应从熟悉的行业、专业领域或真实业务场景出发，围绕具有行业普遍性的复杂任务，构建可复用 Skill、工具集成与运行验证能力。

评审关注的不只是单个 Agent 的能力，而是多 Agent 如何在复杂约束下完成：

- 任务拆解；
- 上下文传递；
- 工具调用；
- 结果验证；
- 执行证据沉淀；
- 安全审计；
- 面向真实企业场景的端到端闭环。

### 1.3 核心参赛要求（PDF 第 1-2 页）

作品应围绕真实企业场景，设计不少于 3 个不同职能 Agent 的完整闭环，并把关键能力沉淀为可复用 Skill，而不是一次性脚本或单次演示。

重点体现：

- 多 Agent 协同完成复杂任务；
- Skill 可复用与工程化封装；
- 工具、系统或云产品的稳定接入；
- 上下文管理与执行证据沉淀；
- 安全边界、审批、回滚与审计机制；
- 开放/开源计划与长期成长价值。

### 1.4 适合参赛团队（PDF 第 2 页）

- 具备多 Agent 系统设计能力的开发者团队；
- 熟悉云产品、企业系统、DevOps、ITSM、FinOps 或安全系统集成的团队；
- 对运维、安全、成本治理、容量治理等企业复杂场景有理解的团队；
- 熟悉业务系统、数据平台、研发工具链或行业应用集成的团队；
- 理解复杂任务协同、流程自动化、知识沉淀、风险控制、效率提升或体验优化的团队；
- 具备工程实现、工具链集成和 Demo 构建能力的高校实验室、开源团队、企业团队或独立 AI Builder；
- 有开源项目建设、技术文档或社区协作经验者优先。

## 04 报名阶段：报名、组队与选题方向

### 4.1 报名信息（PDF 第 4 页）

- 报名人姓名；
- 国家/地区；
- 手机号；
- 常用邮箱；
- 队伍名称；
- 团队总人数；
- 团队成员、身份及联系方式；
- 意向赛道。

### 4.2 组队规则（PDF 第 4 页）

1. 可个人参赛；组队时团队不超过 3 人。
2. 初赛队伍提交后不得变更成员信息。
3. 进入复赛后，所有成员需要实名核验。未完成核验或信息不实，组委会可取消后续参赛或获奖资格。

### 4.3 开放式选题（PDF 第 5-6 页）

示例方向仅用于启发，不限制参赛范围。有效选题应来自真实需求，体现多 Agent 在任务拆解、协同执行、工具调用、结果验证和经验沉淀中的价值，并有沉淀为 Skill、工具接口或开源能力的潜力。

#### 方向一：零人工运维

- 多源告警聚合与降噪；
- 自动根因定位；
- 修复建议生成与执行；
- 服务恢复验证；
- 事故复盘与知识沉淀。

#### 方向二：智能客服自主闭环

- 邮件、在线客服、电话转写、社媒评论等多渠道工单/会话聚合；
- 意图识别与自动分类分级；
- 退款、换货、账户变更等处理方案生成和执行；
- 结果核验与客户满意度确认；
- 疑难案例复盘与知识库沉淀。

#### 方向三：软件研发全流程协同

- Issue、日志、用户反馈等需求或缺陷聚合；
- 代码缺陷定位和影响分析；
- 修复方案生成和自动编码；
- 测试验证与灰度发布确认；
- 上线复盘与研发知识沉淀。

#### 方向四：金融风控与理赔自动化

- 交易、征信、舆情、投诉等风险信号聚合；
- 风险/欺诈根因定位和影响分析；
- 理赔或授信建议生成与执行；
- 结果核验与合规审计；
- 风险事件复盘与知识沉淀。

## 08 作品技术要求

> PDF 第 10-11 页。初赛可先说明设计；复赛、决赛需要形成可运行、可验证材料。

### 8.1 多 Agent 协同

- 至少 3 个不同职能 Agent；
- 每个 Agent 有清晰身份定义；
- Agent 通过协作完成端到端任务闭环；
- 以 AgentTeams 为协同设计基点；
- 说明角色编排、任务拆解、上下文传递、协同执行和状态追踪如何映射到 AgentTeams。

### 8.2 Agent Identity 清单

需说明每个 Agent 的身份属性、能力边界和协同关系，格式见附录 A。

### 8.3 多 Agent 闭环

方案需要说明：

1. **任务输入**：接收告警、工单、日志、账单、安全事件或其他企业任务；
2. **任务拆解**：主控 Agent 或协同框架拆给不同职能 Agent；
3. **上下文传递**：传递历史、工具结果和中间结论；
4. **工具调用**：调用 Skill、MCP、云产品、企业系统、知识库或外部接口；
5. **结果验证**：验证修复、安全处置、成本优化等结果；
6. **执行证据沉淀**：保存日志、Trace、Metrics、报告、截图等证据；
7. **审批与回滚**：高风险动作有人工确认、审批、回滚和审计；
8. **经验沉淀**：把结果、复盘或经验规则沉淀成可复用能力。

## 09 Skill、MCP、RAG 与可观测要求

### 9.1 Skill：必选项（PDF 第 11 页）

Skill 是任务能力抽象层，不是一次性 Agent 行为描述。每个方案至少提供核心 Skill 清单，并说明：

- 名称和用途；
- 输入与输出；
- 调用条件；
- 依赖工具；
- 失败处理；
- 安全边界；
- 复用价值；
- 与多 Agent 流程的关系。

原文称可使用阿里云官方用云 Skill，也可把自己的关键能力沉淀为 Skill。FAQ 的口径见本文“阅读提醒”。

### 9.2 MCP：推荐可选项（PDF 第 11-12 页）

MCP 用于连接云产品、企业系统、数据库、知识库、工单、CI/CD、监控系统等外部工具。Skill 负责能力抽象，MCP 负责工具连接。

不使用 MCP 时，必须给出等价工具集成契约：

- 协议和调用入口；
- 鉴权方式；
- 参数 Schema 和返回结构；
- 权限范围；
- 错误处理、失败重试和降级；
- 幂等控制；
- 审计记录；
- 迁移到 MCP 的成本。

评审不要求替代方案已经实现 MCP Server，但需要证明未来只需做协议适配，而不是重做工具调用链。

### 9.3 可观测：推荐可选项（PDF 第 12-13 页）

如使用可观测能力，应说明采集方式、语义规范、数据类型、后端存储和使用效果。建议至少覆盖 1-2 类：

1. **Trace**：记录 Agent、Skill、MCP、RAG、LLM 等 Span，尽量遵循开源语义标准；
2. **Log**：结构化记录决策依据、失败原因、权限校验和审批事件，通过 `TraceId` 关联；
3. **Metrics**：对话/会话数、端到端时延、TTFT、Token、Tool 成功率等流量、性能、成本和可靠性指标。

可基于观测数据进行规则评估、LLM-as-Judge、Agent-as-Judge 或人工标注，结果回流 Dataset，或用于优化 Prompt、Skill、RAG、MCP 和模型。

### 9.4 RAG 与上下文增强：推荐可选项（PDF 第 13 页）

RAG 适用于知识库、历史记录、规范、业务数据、Runbook、评审证据或工具结果检索。推荐链路是：MCP 接入数据源，Skill 封装检索、证据对齐和写入，Agent 判断证据是否充分。

从以下 4 项至少实现 2 项：

1. Agent 记忆存储；
2. 知识库 RAG；
3. 共享状态管理；
4. 轨迹可观测。

明确不使用 RAG 时，需要在除“知识库 RAG”外的其他 3 项中至少实现 2 项，并论证上下文机制有效。

## 17 官方示例 Demo：OpsPilot Zero

> PDF 第 23-35 页。以下是官方提供的作品示例，不是所有参赛项目必须照搬的架构或技术栈。

### 17.1 项目定位（PDF 第 23-24 页）

**名称**：OpsPilot Zero——面向千行百业云上与自建 IDC 业务故障的零人工运维多 Agent 排查与自愈系统。

| 方面 | 示例内容 |
|---|---|
| 赛题定位 | 多 Agent 协同、Skill 工程化、工具接入与审计、开源复用 |
| 真实痛点 | 客诉模糊、数据分散或缺失、环境差异大、专家经验难规模化 |
| 项目价值 | 5-10 分钟初诊、低风险受控自愈、输出证据缺口、沉淀 Runbook/Skill |

示例指标：人工初排常见 30-60 分钟，Demo 初诊目标 5-10 分钟，低风险动作零人工值守，关键操作 100% 留痕。

### 17.2 Demo 场景（PDF 第 25 页）

模拟电商订单服务异常：用户反馈 10:15 后下单失败、支付页卡住。流程从客诉进入，经过 5xx 升高、事故归并、变更定位、回滚计划和恢复验证。

证据包括：

- 网关 `/api/order/create` 5xx 升高；
- `order-service` p99 延迟升高；
- 数据库连接池耗尽；
- 库存与支付调用超时；
- 配置变更 `db.pool.maxSize: 50 -> 8`。

模拟环境包括 Kubernetes/ACK/自建集群、Nacos、Higress/Ingress、MySQL/RDS。

### 17.3 总体架构（PDF 第 26-27 页）

```text
用户/客户入口：客诉、告警、工单、恢复报告
→ AgentTeams 编排层：任务拆解、共享状态、路由、升级
→ 多 Agent 层：入口、指挥、RCA、数据建议、计划、执行、验证
→ Skill 层：告警归并、RAG、根因分析、风险控制、验证、复盘
→ MCP/适配器：Nacos、K8s、网关、CMS、AgentLoop、工单、知识库
→ 证据与治理：Incident State、行为审计、可观测、向量知识库
```

Agent 不裸调工具，而是通过 Skill 和 MCP/适配器形成可治理调用链。Incident State 保存上下文、任务状态、幂等键、审批和证据索引；AgentLoop 记录 Agent、Skill、工具与 LLM 的 Trace、Log、Metrics。

### 17.7 RAG、上下文与证据（PDF 第 32 页）

```text
输入归并 → 上下文整理 → RAG 检索 → 证据评分 → 输出闭环
```

- 强证据：配置变更与异常时间一致，日志出现连接池耗尽；
- 弱证据：部分 Trace 超时但采样不足；
- 缺失证据：缺少慢 SQL、连接池水位和 JVM 指标。

数据不足时输出证据等级、缺口和采集建议，不编造结论。

### 17.8 可观测与安全（PDF 第 33 页）

- 每次任务拆解、Skill 调用和工具调用可回放；
- 指标包括任务完成度、工具选择合理性和 RAG 召回相关性；
- 使用 Golden/Badcase 数据集回放比较 Agent 版本；
- 安全执行前置条件包括白名单、幂等键、灰度、审批记录和自动回滚点；
- 自动化等级从只读诊断、低风险自动执行、灰度加审批，到只生成方案。
