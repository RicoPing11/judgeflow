## 1. 实现范围

- 新增一个只服务比赛固定流程的单页，未建设通用后台、登录、权限或配置中心。
- 在现有 Python 项目中新增标准库 HTTP 入口和四个固定闭环接口：创建 Demo、读取 Demo、记录 Human APPROVE、创建固定 TIMEOUT 失败场景。后续 P0/P1 产品化改版又在同一服务中增加了运行监控、案件、规则、审批和回放的七类只读投影；完整现行接口以 `app/demo/server.py` 和产品化页面交接文档为准。
- 后端复用既有 `JudgeFlowKernel`、五工具 FastMCP 契约、八个固定领域 Agent runner、确定性 Python 回放器和八张 PostgreSQL 表。
- 未新增 Agent、业务房间、数据库表、MCP 工具、Skill、微服务、框架、RAG、消息队列、状态中心或 guard。
- 未修改或复制 `opspilot-zero-demo`，未删除或重建 PostgreSQL、AgentTeams 数据卷和 Matrix 房间，未覆盖阶段五数据。
- 页面不直连数据库、Agent、Matrix 或 MCP；所有正式写入由后端进入 Kernel 验收路径。

## 2. 页面能力

单页按固定讲解顺序展示：案件信息、当前步骤/Agent、调查证据、风险意见、反证意见、独立裁决、冻结原裁决快照、申诉白名单新增证据、OVERTURN、规则与非规则归因、基线/候选规则 Diff、确定性回放指标、Human 审批及完整执行证据。

WorkOrder 表展示 `assignee`、状态、`work_order_id`、`run_id`、`trace_id` 和 `artifact_id`。页面图例与接口明确区分：

- `NOT_STARTED` / 未开始；
- `RUNNING` / 运行中；
- `SUCCESS` / 成功；
- `FAILURE` / 工具或执行失败；
- `NOT_FOUND` 或业务无数据。

失败响应使用明确的 `FAILURE`，不会伪装成空结果。Human APPROVE 按钮只记录绑定具体 proposal 与 replay 的比赛审批 Artifact。
