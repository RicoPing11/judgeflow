后续定向复查最终定位到目录冲突：AgentTeams 将 `config.json` 和 `matrix_channel.py` 同步到 `/root/.copaw-worker/<worker>/.copaw`，但官方 v1.2.0 进程因 `HOME` 指向临时 `agentteams-fs`，CoPaw 实际从另一目录发现插件，导致 Matrix channel 根本没有实例化。`agentteams/copaw-worker-matrix.Dockerfile` 仅在官方入口中导出 `COPAW_WORKING_DIR` 与 `COPAW_SECRET_DIR`，不增加服务、守护进程或包装器；10 个 Worker 资源固定使用该镜像。

动态验收由 Counter 的原生 Matrix 身份向裁决 Team 房发送带 `m.mentions` 的重复风险工单。Risk 的 CoPaw 自动创建了 `matrix--<team-room>` 会话，证明消息已进入 Worker 自动消费路径；数据库仍只有四份 Artifact，没有重复写入。

模型提交阻断的根因是 flash 难以稳定构造完整 ArtifactEnvelope/hash。现有 `artifact.put` 已兼容紧凑领域 payload：后端依据 WorkOrder 绑定 authoritative envelope、producer 与 IDs，并计算 canonical hash，随后仍进入 Kernel 的严格验收。Risk、Counter、Judge 三个 flash Worker 已分别真实返回 HTTP 200，数据库逐项确认对应 WorkOrder `SUCCEEDED` 与 Artifact 存在，未把 HTTP 200 单独当成成功证据。

## 7. 实际 MCP transport

新增的是现有五工具的最小 FastMCP Streamable HTTP transport 适配，不新增业务工具。设计预期由 Higress 原生 key-auth 注入 `X-Mse-Consumer`，并把 `worker-<name>` 规范化为阶段四 Agent ID。独立验收实际证明：在 Higress 未建立时，直连调用者可伪造该 header 并成功读取 WorkOrder。因此当前 transport **没有可信身份边界**；代码已改为默认拒绝启动，只有显式确认位于已认证 Higress 后方才可运行。

以下 `:8765/mcp` JSON-RPC 结果仅证明业务授权逻辑，不证明调用者身份可信：

- 正确 `worker-case-investigator` + 正确 WorkOrder/run/trace：`work_order.get` 成功；
- `worker-risk-prosecutor` 读取该 WorkOrder：`PERMISSION_DENIED`（非 assignee）；
- 正确 Agent + 错误 run：`PERMISSION_DENIED`；
- Manager consumer：`PERMISSION_DENIED`（不是领域 Agent）。

已在 Higress 建立 `mcp-judgeflow` direct-proxy，后端指向 Docker 网络内 `judgeflow-mcp.internal:8765`；MCP 容器未映射宿主端口。只给 8 个领域 Worker Consumer 授权，Manager 与两位 Leader 不授权。动态验证：case-investigator 的 initialize 与 `work_order.get` 为 HTTP 200；Manager 和 adjudication Leader 为 HTTP 403。Worker 随后的真实会话已通过同一路径执行 `work_order.get`、`context.get`、`evidence.search`，`query_type=CONTENT` 返回两条固定事实。当前可信边界依赖 Higress key-auth 与 Docker 网络隔离，`JUDGEFLOW_TRUST_NATIVE_HIGRESS=1` 只是部署断言，本身不是认证机制。
