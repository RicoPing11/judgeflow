# 阶段四验收报告

## 阶段范围

仅实现《JudgeFlow-开发顺序.md》的“阶段 4：八个领域 Agent”。本阶段使用固定本地测试驱动，不接 AgentTeams、Matrix、FastAPI、前端或真实外部接口；未新增数据库表、迁移、MCP 工具、Skill、第九个 Agent、协调 Agent、Human、状态推进工具或规则发布能力，也未进入阶段五。

## 完成内容

- 定义八个不可变最小 Agent 契约，固定身份、职责、Skill/模式、WorkStep、输出 Artifact、允许的 MCP 工具和禁止事项；
- 实现一个只服务固定 Demo 的本地驱动 `FixedAgentRunner`，逐次绑定唯一 WorkOrder、assignee、run 和 trace；
- Agent 只通过阶段三 `JudgeFlowMCPService` 使用授权工具，不直接访问数据库或调用状态推进接口；
- 正式输出复用阶段一 payload Schema 和 `ArtifactEnvelope`，统一经阶段三 `artifact.put` 与阶段二 `JudgeFlowKernel.accept_artifact()` 验收；
- 原案调查仅使用 `E-001`，冻结原案快照也只记录 `E-001`；申诉白名单及申诉 WorkOrder 才使用 `E-APPEAL-001`；
- 固定证据查询显式提供可观察事实。调查 Agent 只复制工具返回的 `observable_facts`，并将观察事实、推断、缺失信息和工具失败分栏；
- 风险与反证 Agent 独立读取同一已验收证据包和锁定规则，拒绝读取对方 Artifact，并校验 fact、evidence 和规则要件绑定；
- 裁决 Agent 必须同时取得已验收的风险意见和反证意见，且只引用已验收证据与锁定规则；
- 申诉 Agent 即使错误网关暴露实时案件材料也会拒绝，只使用冻结原案快照、其中锁定规则和新增证据白名单；
- 归因支持 `EVIDENCE_GAP`、`AGENT_ERROR`、`POLICY_GAP` 和 `POLICY_CONFLICT`，改判仍可归为非规则问题并关闭规则编写；
- 规则作者仅在规则缺口或冲突时生成阶段一有限 Policy DSL 候选版本，拒绝 `SCORING` 和非规则归因，不覆盖基线版本；
- 回放 Agent 只调用 `replay.execute`，原样封装 Python 返回的指标和推荐；逐案结果与标签仅用于绑定核对，不由 Agent 计算或修改。

## 八个 Agent 权限矩阵

| Agent | Skill / 模式 | 允许的 MCP 工具 | 输出 Artifact |
|---|---|---|---|
| `case-investigator` | `case-investigation` | `work_order.get`、`context.get`、`evidence.search`、`artifact.put` | `EVIDENCE_BUNDLE` |
| `risk-prosecutor` | `case-deliberation / RISK` | `work_order.get`、`context.get`、`artifact.put` | `RISK_ARGUMENT` |
| `counter-reviewer` | `case-deliberation / COUNTER` | `work_order.get`、`context.get`、`artifact.put` | `COUNTER_ARGUMENT` |
| `independent-judge` | `case-deliberation / DECISION` | `work_order.get`、`context.get`、`artifact.put` | `DECISION_RECORD` |
| `appeal-reviewer` | `case-deliberation / APPEAL` | `work_order.get`、`context.get`、`artifact.put` | `APPEAL_DECISION` |
| `case-attributor` | `policy-evolution / ATTRIBUTION` | `work_order.get`、`context.get`、`artifact.put` | `ATTRIBUTION_REPORT` |
| `policy-author` | `policy-evolution / DRAFTING` | `work_order.get`、`context.get`、`artifact.put` | `POLICY_PROPOSAL` |
| `replay-analyst` | `case-replay` | `work_order.get`、`context.get`、`replay.execute`、`artifact.put` | `REPLAY_REPORT` |

## 主 Agent 检查

主 Agent 检查了代码、权限边界、数据隔离、Schema/Kernel/MCP/Skill 复用和改动范围。`app/agents` 不导入 SQLAlchemy、数据库模型、`JudgeFlowKernel` 或状态推进接口；只调用阶段三既有五工具的授权子集。未发现第九个 Agent、AgentTeams/Matrix 资源、新 MCP/Skill、数据库或阶段五内容。

## 独立验收与返修

独立验收 Agent 严格只读检查并运行测试。首轮发现：原案提前使用申诉新增证据、驱动从证据元数据推造观察事实、所有改判被简化为规则缺口，以及完整提交拒绝和回放逐案结果核对覆盖不足。

返修后：

- 分离原案 `E-001` 与申诉新增证据 `E-APPEAL-001`；
- 固定证据显式返回 `observable_facts`，Agent 校验 fact/evidence/clause 绑定；
- 改判可归为非规则问题并停止草案；
- 补充完整 runner、`artifact.put` 和回放逐案结果/标签不变测试；
- 修正冻结原案快照及权限负测中的证据 ID。

最终独立复验结论为 `PASS`：阶段四 `26 passed`，全量 `124 passed, 1 skipped, 1 warning`；首轮发现全部关闭，未发现返修引入新问题，建议批准阶段四。
